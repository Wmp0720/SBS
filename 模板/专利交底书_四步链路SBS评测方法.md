## 2. 技术背景

### 2.1 现有技术问题

随着大语言模型（LLM）技术的快速发展，如何高效、客观地评估不同模型在真实用户对话场景下的表现，已成为模型迭代与产品落地的关键步骤。

现有的LLM评测方法主要包括：

1. 单步LLM裁判方法：
   - 直接调用一个"裁判模型"，输入用户问题及两个模型的回答，输出胜/平/负结论。
   - 存在的问题：
     - 裁判模型往往比人类更"严格""挑剔"，与人类标注尺度不一致，导致评测结果不可信；
     - 单步决策缺乏可解释性，无法区分"事实收集过程"和"裁决过程"，难以调试与复用；
     - 评测结果不稳定，同一组输入可能产生不一致的输出。

2. 基于规则/简单打分的自动评测：
   - 利用预定义规则或粗粒度打分模型，对回答进行"对不对""长不长"等打分。
   - 存在的问题：
     - 对复杂多轮对话、主观体验维度（如拟人化程度、阅读体验）刻画不足；
     - 很难对齐真实的人类标注习惯；
     - 规则固定，无法适应不同场景和问题类型。

3. 人工标注方法：
   - 由标注员逐条阅读问答数据，对模型回答进行满意度评估与胜负判定。
   - 存在的问题：
     - 成本高、效率低；
     - 容易受到标注员主观偏好和疲劳的影响；
     - 难以大规模、长期稳定执行。

### 2.2 现有技术方案

现有技术中，LLM评估系统主要包括以下几种：

1. 单模型评分系统：针对单个模型的输出进行评分，如BLEU、ROUGE等自动评估指标，但缺乏模型间的直接对比。

2. 简单对比系统：对两个模型的输出进行简单对比，但缺乏结构化的评估框架和可解释的决策过程。

3. 规则驱动系统：基于预定义规则进行评估，但规则制定成本高，且无法自适应新的场景和问题类型。

这些现有技术方案都存在各自的局限性，无法满足对LLM进行全面、准确、高效、可解释的Side-by-Side对比评估需求。

## 3. 发明内容

### 3.1 发明目的

本发明的目的在于提供一种基于四步链路的Side-by-Side大模型对话评测方法及系统，以解决现有技术中存在的评测结果不稳定、缺乏可解释性、人机不一致、评测流程不可拆解等问题。

### 3.2 技术方案概述

本发明提供了一种基于四步链路的Side-by-Side大模型对话评测方法及系统，该方法将评测流程拆分为四个固定顺序的步骤：

1. 步骤S1：单模型主要问题标注
   - 分别对自研模型和竞品模型进行独立的主要问题标注，输出结构化的问题标签。

2. 步骤S2：主要问题到二级满意度的模糊映射
   - 通过模糊标签桶和规则推理引擎，将主要问题标签自动映射为二级满意度等级（弱智/不合格/合格/优质）。

3. 步骤S3：CoT第一步——SBS对比分析（事实收集）
   - 基于两个模型的对话内容，进行Side-by-Side对比分析，只收集事实与问题标签，不进行胜负裁决，输出结构化的"案件档案"。

4. 步骤S4：CoT第二步——最终裁决
   - 基于步骤S3收集的"案件档案"和步骤S1的单模主要问题，进行最终的胜/平/负裁决，并输出裁决理由。

通过将"裁判思维"拆解为"事实归档+法官裁决"两个阶段，本发明实现了评测流程的可解释、可调试、可复用，显著提高了评测结果的稳定性和人机一致性。

### 3.3 技术方案详细描述

#### 3.3.1 系统架构

本系统的架构包括以下几个主要组件：

- 单模标注模块：执行步骤S1，对单个模型进行主要问题标注
- 满意度映射模块：执行步骤S2，将问题标签映射为满意度等级
- CoT对比分析模块：执行步骤S3，进行事实收集和对比分析
- CoT最终裁决模块：执行步骤S4，进行最终胜负裁决
- 规则引擎模块：提供标签归一化和规则推理能力

#### 3.3.2 步骤S1：单模型主要问题标注

功能描述：分别对自研模型和竞品模型进行独立的主要问题标注，为后续步骤提供基础数据。

具体实现：

1. 数据提取：
   - 分别提取自研模型和竞品模型的多轮对话历史与当前轮回答。
   - 构造成包含"上下文（不含最后一轮）+ 本轮问答"的文本格式。

2. Prompt构造：
   - 使用create_single_model_prompt函数构造单模标注Prompt。
   - Prompt中包含以下要素：
     - 当前度量维度说明（如技能、文本生成、知识问答、聊天等）；
     - 该维度下的优质标签集合；
     - 单个大模型主要问题标签全集（预定义的标签体系）；
     - 学习到的评测指南（learned_guidelines，如果有）；
     - 失败触发器知识库（loss_triggers，如果有）。

3. 模型调用与结果解析：
   - 调用评测LLM（如GPT-4、Claude等），获取模型输出。
   - 解析输出为结构化JSON格式，至少包含以下字段：
     - "主要问题"：从预定义标签集中选取1-3个标签，多个标签用中文逗号分隔；
     - "优质弱智主要问题"：若主要问题包含"12弱智"或"14优质"，则在此字段给出具体原因标签；
     - "标注理由"：简要说明做出以上判断的理由。

4. 输出结果：
   - 自研模型的主要问题标签：a_single_main_issues
   - 竞品模型的主要问题标签：b_single_main_issues
   - 自研模型的优质弱智主要问题：a_qzrz
   - 竞品模型的优质弱智主要问题：b_qzrz

#### 3.3.3 步骤S2：主要问题到二级满意度的模糊映射

功能描述：通过模糊标签桶和规则推理引擎，将主要问题标签自动映射为二级满意度等级。

具体实现：

1. 标签拆分：
   - 将步骤S1输出的"主要问题"标签字符串（可能包含多个标签，用中文逗号分隔）通过_split_labels函数拆分为标签集合。

2. 标签归一化（桶化）：
   - 使用bucket_of函数将每个标签归一到有限的"问题桶"。
   - 桶化优先级：
     - 若标签前缀为维度优质前缀（如"技能_"、"生文_"、"问答_"、"闲聊_"），则直接归为"14优质"桶；
     - 若标签已含"12弱智"、"14优质"、"13无问题"等显式前缀，则直接归为对应桶；
     - 否则，通过KEYWORD2BUCKET映射表进行关键词匹配（如"内容错误"→"2内容质量差_1.内容错误"）；
     - 若仍无法匹配，则根据包含关系回退到更粗粒度桶（如包含"内容质量差"→"2内容质量差"）；
     - 最后兜底为"标签字符串下划线前的主类部分"。

3. 满意度推理：
   - 使用map_main_issues_to_satisfaction函数进行满意度推理。
   - 推理逻辑：
     - 遍历从"弱智"到"优质"的等级（按严重程度排序）；
     - 结合标签原始字符串前缀与桶前缀匹配，确定最合适的满意度等级；
     - 使用配置中的satisfaction_map和severity_order进行匹配。
   - 输出结果：
     - 满意度等级：弱智/不合格/合格/优质/未选中
     - 命中模式原因：说明为何得到该满意度等级

4. 输出结果：
   - 自研模型的二级满意度：a_satisfaction
   - 竞品模型的二级满意度：b_satisfaction

#### 3.3.4 步骤S3：CoT第一步——SBS对比分析（事实收集）

功能描述：基于两个模型的对话内容，进行Side-by-Side对比分析，只收集事实与问题标签，不进行胜负裁决。

具体实现：

1. Prompt构造：
   - 使用create_sbs_analysis_prompt函数构造SBS对比分析Prompt。
   - Prompt中包含以下要素：
     - 角色设定：明确为"证据书记员/分析员"，强调只做事实收集，不做裁决；
     - 当前度量维度说明；
     - SBS标签集合（专门用于Side-by-Side对比的标签体系）；
     - 失败触发器清单（loss_triggers）；
     - 胜利模式清单（win_patterns）；
     - 学习到的评测指南（learned_guidelines，如果有）；
     - 自研模型和竞品模型的上下文与当前轮回答。

2. 模型调用与结果解析：
   - 调用评测LLM，获取模型输出。
   - 解析输出为结构化JSON格式，包含以下字段：
     - "大模型A_SBS主要问题"：从SBS标签集合中选择，可多选，用中文逗号分隔；
     - "大模型B_SBS主要问题"：从SBS标签集合中选择，可多选，用中文逗号分隔；
     - "大模型A_命中的失败触发器"：从loss_triggers中选取，数组格式；
     - "大模型B_命中的失败触发器"：从loss_triggers中选取，数组格式；
     - "大模型A_符合的胜利模式"：从win_patterns中选取，数组格式；
     - "大模型B_符合的胜利模式"：从win_patterns中选取，数组格式。

3. 输出结果：
   - 结构化的"案件档案"：analysis_json
   - 该档案包含所有对比分析的事实，但不包含胜负结论。

#### 3.3.5 步骤S4：CoT第二步——最终裁决

功能描述：基于步骤S3收集的"案件档案"和步骤S1的单模主要问题，进行最终的胜/平/负裁决。

具体实现：

1. Prompt构造：
   - 使用create_final_judgment_prompt函数构造最终裁决Prompt。
   - Prompt中包含以下要素：
     - 角色设定：明确为"高级评测法官"；
     - 步骤S3输出的"案件档案"（analysis_json的JSON字符串形式）；
     - 步骤S1得到的单模主要问题（a_single_main_issues和b_single_main_issues）；
     - 详细的判定规则：
       - 第一优先级：致命错误裁定（Fatal Error Ruling）
         - 任何一方命中失败触发器，直接判负；
         - 若双方都命中，则问题更严重或数量更多的一方判负。
       - 第二优先级：显著优势裁定（Clear Advantage Ruling）
         - 若双方均无致命错误，则符合胜利模式更多或优势更具决定性的一方判胜。
       - 第三优先级：问题严重性与数量对比（Issue Severity & Count Comparison）
         - 标签严重性排序：12弱智 > 1未提供需要信息 > 2内容质量差_1.内容错误 > 2内容质量差 = 3多轮效果不佳 > 4冗长 = 5简略 = 6语言表达不佳 > 7格式及呈现不佳 = 8内容要素不佳 > 13无问题 > 14优质
         - 判定顺序：比等级 → 比数量 → 比总数
       - 最终裁定：若以上都无法区分，则判为"平"。

2. 模型调用与结果解析：
   - 调用评测LLM，获取模型输出。
   - 解析输出为结构化JSON格式，包含以下字段：
     - "大模型A竞品对比"：胜/平/负
     - "裁判说明"：一句话简洁解释裁决理由

3. 输出结果：
   - 最终胜负结论：sv_compare（胜/平/负）
   - 裁判说明：tiebreak_reason

#### 3.3.6 模糊标签桶与规则推理引擎

功能描述：提供标签归一化和规则推理能力，支持步骤S2和步骤S4的自动推理。

具体实现：

1. 关键词到桶名映射表（KEYWORD2BUCKET）：
   - 维护一个映射表，将非规范标签或自然语言描述归一为有限的"问题桶"。
   - 示例映射：
     - "弱智" → "12弱智"
     - "内容错误"、"实体错误" → "2内容质量差_1.内容错误"
     - "冗长"、"拓展过多"、"篇幅过长" → "4冗长"
     - "简略"、"篇幅过短"、"拓展过少" → "5简略"

2. 桶化函数（bucket_of）：
   - 按优先级处理标签：
     - 维度优质前缀识别
     - 显式前缀识别
     - 关键词映射匹配
     - 包含关系回退
     - 兜底处理

3. 满意度映射函数（map_main_issues_to_satisfaction）：
   - 输入：主要问题标签字符串
   - 处理：标签拆分 → 桶化 → 匹配satisfaction_map → 确定满意度等级
   - 输出：满意度等级 + 命中模式原因

4. 胜负规则判定函数（decide_winloss_by_rules）：
   - 输入：两个模型的主要问题标签
   - 处理：
     - 获取双方最严重问题桶（_top_severity_bucket）
     - 依据severity_order比较严重级别
     - 若级别相同，比较该级别下的问题数量
     - 若仍无法区分，比较总问题数
     - 若仍无法区分，返回需裁判模型介入的标志
   - 输出：胜/负/平 + 判定理由 + 是否需要裁判模型

### 4.3 系统运行

主流程伪代码：

```
for each row in dataset:
    # 步骤S1：单模型主要问题标注
    prompt_a = create_single_model_prompt(...)
    single_a = call_llm(prompt_a)
    a_single_main_issues = parse_json(single_a)["主要问题"]
    
    prompt_b = create_single_model_prompt(...)
    single_b = call_llm(prompt_b)
    b_single_main_issues = parse_json(single_b)["主要问题"]
    
    # 步骤S2：主要问题到二级满意度映射
    a_satisfaction, _ = map_main_issues_to_satisfaction(a_single_main_issues, rules)
    b_satisfaction, _ = map_main_issues_to_satisfaction(b_single_main_issues, rules)
    
    # 步骤S3：CoT第一步——SBS对比分析
    analysis_prompt = create_sbs_analysis_prompt(...)
    analysis_res = call_llm(analysis_prompt)
    analysis_json = parse_json(analysis_res)
    
    # 步骤S4：CoT第二步——最终裁决
    judgment_prompt = create_final_judgment_prompt(analysis_json, a_single_main_issues, b_single_main_issues, rules)
    judgment_res = call_llm(judgment_prompt)
    final_result = parse_json(judgment_res)
    
    # 整合结果
    result = {
        "大模型A二级满意度": a_satisfaction,
        "大模型B二级满意度": b_satisfaction,
        "大模型A竞品对比": final_result["大模型A竞品对比"],
        "LLMs_标注理由": final_result["裁判说明"],
        ...
    }
```

   - 包含所有中间结果（单模主要问题、SBS主要问题、失败触发器、胜利模式等）

## 5. 技术效果

### 5.1 直接技术效果

1. 提高评测结果稳定性：
   - 通过固定四步流程，确保每次评测都经过相同的步骤，减少随机性。
   - 通过中间结果的持久化，可以追溯和复现评测过程。

2. 提高可解释性：
   - 每一步都有明确的输入和输出，可以清楚地看到评测过程。
   - 最终裁决基于结构化的"案件档案"，可以明确说明裁决依据。

3. 提高可调试性：
   - 可以逐步检查中间结果，快速定位问题所在。
   - 可以单独测试和优化每个步骤。

4. 提高人机一致性：
   - 通过多步验证和规则推理，减少评测偏差。
   - 通过模糊标签桶，容忍标签的噪声和多样性。

### 5.2 间接技术效果

1. 降低评测成本：
   - 自动化评测流程减少人工标注需求。
   - 可复用的评测流程提高评测效率。

2. 支持模型优化：
   - 详细的评测结果可以为模型优化提供有价值的反馈信息。
   - 可解释的评测过程有助于理解模型表现。

3. 标准化评测流程：
   - 提供了一种标准化的Side-by-Side评测流程。
   - 有助于提高评测的一致性和可比性。

## 6. 技术关键点和保护要点

### 6.1 技术关键点

1. 四步固定链路：
   - 单模标注 → 满意度映射 → CoT对比分析 → CoT最终裁决的固定顺序。
   - 每步的输入输出数据结构明确。

2. 事实收集与裁决分离：
   - CoT第一步只收集事实，不做裁决。
   - CoT第二步基于事实档案做裁决。

3. 模糊标签桶机制：
   - 关键词到桶名的映射。
   - 标签归一化的优先级规则。

4. 规则推理引擎：
   - 满意度自动推理。
   - 胜负规则自动判定。

### 6.2 保护要点

1. 四步固定链路的评测方法：包括四个步骤的具体实现方法和数据流转。

2. 事实收集与裁决分离的CoT机制：包括分析员阶段和法官阶段的具体实现。

3. 模糊标签桶与规则推理引擎：包括标签归一化和规则推理的具体算法。

4. 系统整体架构：各模块之间的交互方式和系统整体工作流程。

## 7. 其他需要说明的事项

### 7.1 可扩展方向

1. 评测维度扩展：可以根据需要增加新的评测维度和标签体系。

2. 规则引擎优化：可以优化标签桶映射表和规则推理逻辑。

3. 多模型支持：可以支持多个模型的对比评测。

### 7.2 潜在风险

1. 模型依赖：系统依赖于评测LLM的性能，模型性能下降可能影响评测结果。

2. 规则维护：标签体系和规则需要定期维护和更新。

3. 计算资源需求：大规模数据评测可能需要较多的计算资源。

### 7.3 解决方案

1. 模型冗余：可以使用多个评测模型进行评估，提高评测的鲁棒性。

2. 规则版本管理：建立规则版本管理机制，支持规则的迭代和回滚。

3. 资源优化：优化算法和数据处理流程，降低计算资源需求。
